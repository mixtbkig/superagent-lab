动手实践：写插件、用 SDK

看懂了不等于会。这一章把前 18 章的知识拧成两件可落地的事：给 DSH 加一个工具，以及用 SDK 从外部驱动一个 DSH agent。所有步骤都来自仓库里的 cookbook，代码是示意，但结构和真实做法一致。

🎯 学完这一章，你会做
  • 从源码把 DSH 跑起来；
  • 新增一个工具包，并让它出现在 agent 的工具列表里；
  • 用插件注册一个监听器 / 一个 LLM 适配器（知道挂哪）；
  • 用 TypeScript / Python SDK 从外部启动并驱动一次运行。
🧸 小学生版：第一次给机器人装零件

你已经看懂了机器人的说明书（前 18 章）。现在动手：先把它装好通电（跑起来），再给它装一个新零件（加工具），最后用遥控器从外面指挥它（用 SDK）。

第一步：把 DSH 跑起来

README「从源码运行」
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
pnpm install
pnpm run build
pnpm dsh web            # 默认 http://127.0.0.1:3080，并打开浏览器

或者直接用 npm 安装的版本：

npx @deepseek-ai/dsh web
💡 小提示

从源码运行时，pnpm run build 会准备构建产物；pnpm dsh web 直接用这些产物，不会重新构建。开发时可以用 pnpm run dev:web，它会在源码修改时重建 client bundle。

第二步：加一个工具

回顾第 8 章：工具 = ToolDefinition，注册到 ctx.tools。下面是一个完整的「查天气」工具插件示意（包名、路径按 DSH 约定）：

packages/my-tools/weather/src/index.ts（示意）
import { defineTool } from '@deepseek-ai/dsh-tools'
import type { Context } from '@deepseek-ai/cordis'

export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.effect(() => ctx.tools.register(defineTool({
    name: 'weather',
    description: 'Get the current weather for a city',
    parameters: {
      city: { type: 'string', required: true },
    },
    output: {
      schema: { type: 'object', additionalProperties: false,
        properties: { tempC: { type: 'number' }, sky: { type: 'string' } } },
      render: (_args, v) => [{ type: 'text', text: `${v.sky}, ${v.tempC}°C` }],
    },
    async execute({ city }, exec) {
      // 真实实现里应使用 ctx.fs / ctx.web 等 seam，并转发 exec.signal
      return { tempC: 22, sky: 'sunny' }
    },
    timeoutMs: 8_000,
    isConcurrencySafe: () => true,
  })))
}

然后把它挂进 profile。最简做法是在你自己的 profile 的 cordis.patch.yml 里加一行：

- insert:
    - id: tool-weather
      name: '@my/tool-weather'
      config: {}
💡 为什么这么简单？

因为工具注册是「可逆副作用」：插件 mount 时 register 返回一个 disposer，卸载时自动撤销。schemas() 会自动把它的 schema 加进下一次提示词组装。你不需要改 agent-loop、不需要改内核——这正是第 2、3 章反复强调的。

第三步：其它扩展点（挂哪）

你想做写在哪里

第四步：用 SDK 从外部驱动

如果你不想启动 Web，而是想让自己的程序调用 DSH，用 SDK。TypeScript SDK 会解析同版本的 dsh 依赖并以 sdk profile 启动一个子进程，通过 stdio JSON-RPC 通信：

TypeScript SDK 用法（示意）
import { DeepHarness } from '@deepseek-ai/dsh-sdk-client'

const harness = new DeepHarness({ /* cwd, profile 等 */ })
const session = await harness.startSession({ cwd: process.cwd() })

// 发一条用户消息，流式读取事件
for await (const ev of session.send('把这个仓库的测试跑一遍')) {
  if (ev.type === 'assistant/message') console.log(ev.data.message)
  if (ev.type === 'tool/call') console.log('调用工具', ev.data.name)
}
await harness.close()

Python 用法类似：SDK 运行时 wheel 把普通 dsh CLI 打包成平台相关包，客户端默认以显式 Harness home 启动 dsh --profile sdk。

第五步：验证与收尾

按 DSH 的工程约定，改完代码至少要跑：

pnpm run typecheck        # 类型
pnpm run lint             # 风格
pnpm run test             # 单元测试
pnpm run build:check      # 构建产物与契约检查
pnpm run doc-sync         # 若改了文档 / 类型 / 生成目录
⚠️ 两个容易踩的坑
  • 版本会变：DSH 处于「开发者预览」，破坏性变更常见。上面代码是结构示意，字段名请以你 clone 的版本源码为准。
  • 不要绕过 dsh profile 启动：仓库明确规定，只有 dsh profile 能启动受支持的 Node 应用；package bin、demo、内联应用树都是被拒绝的路径。

🧪 小测验
给 DSH 新增一个工具，最核心的动作是？
答案：B。工具就是注册表里的一条 ToolDefinition；schema 会自动进入下一次提示词组装，无需改循环。
🧪 小测验
TypeScript SDK 驱动 DSH 时，两者靠什么通信？
答案：B。SDK 启动一个 dsh --profile sdk 子进程，通过 stdio JSON-RPC 通信，进程隔离、可跨语言。
