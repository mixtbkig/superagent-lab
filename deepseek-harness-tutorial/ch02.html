一切皆插件：Cordis

DSH 底层是一个叫 Cordis 的插件框架。它的核心思想只有一句：没有特权内核，产品的一切都是插件——模型适配器、工具注册表、会话日志、甚至 Agent 循环本身，都可以从配置里换掉。理解 Cordis，是读懂 DSH 源码的第一把钥匙。

🎯 学完这一章，你会明白
  • Cordis 的 5 个核心概念：插件、上下文、依赖注入、类型化事件、可逆副作用；
  • ctx.tools / ctx.llm 这类「服务」到底是什么；
  • 5 种事件分发模式（emit / waterfall / parallel / serial / bail）的区别；
  • 为什么「注册就是副作用」能让热重载与清理变得干净。
🧸 小学生版：乐高 + 插座板

把整个 harness 想成一间没有承重墙的乐高房间。每件家具（插件）都不是钉死在地上的，而是插在一块插座板（上下文 ctx）上。

  • 插座板上有很多编号插口：ctx.tools、ctx.llm、ctx.sessions……谁占了某个插口，谁就提供这项服务。
  • 家具会写「我需要几号插口」（inject）。没通电它就不启动，电一通它自动开始工作——你不用手动排启动顺序。
  • 拔掉家具，插座自动断电、电线自动收回（effect）。不会留下半截电线。
  • 家具之间靠「广播」沟通（事件）：广播一句「有人要调用工具啦」，感兴趣的家具自己举手。

五个核心概念

概念一句话类比
插件 Plugin一个实现 Service 的对象：函数 apply(ctx) 或 Service 子类一件家具
上下文 Context服务的容器，一项服务占据稳定的 ctx.<key>插座板 / 总机

上下文是一棵树

Cordis 的 ctx 不是平的，而是一棵插件树。根上下文派生出一层层子上下文；子上下文继承父的服务，但可以局部覆盖、局部注册。DSH 正是用这棵树实现了「全局」与「按 agent 作用域」两种注册（后面章节会大量用到）。

服务（Service）长什么样

一项服务就是一个带 ctx.<key> 的类。比如工具注册表 ctx.tools 提供 register() / schemas() / execute()；会话存储 ctx.sessions 提供创建与打开会话。其他插件从不 import 具体实现，而是根据 key 去上下文里查：

一个最小插件：注入服务、注册一个工具、监听一个事件（示意）
import { Service, Context } from '@deepseek-ai/cordis'

export const inject = ['tools', 'llm']        // ① 声明依赖：等这两个服务就绪

export function apply(ctx: Context) {
  // ② 注册一个服务（占据一个 ctx key）
  ctx.set('greeter', new GreeterService(ctx))

  // ③ 注册是可逆副作用：disposer 会在插件卸载时自动执行
  ctx.effect(() => ctx.tools.register({
    name: 'hello',
    description: 'say hello',
    parameters: {},
    output: { schema: { type: 'string' }, render: (_a, v) => [{ type: 'text', text: v }] },
    async execute() { return 'hello, world' },
  }))

  // ④ 监听类型化事件；waterfall 监听器必须调用 next() 才能把链传下去
  ctx.on('tools/pre-execute', async (exec, next) => {
    ctx.logger.info('about to run', exec.name)
    return next()          // 不调用 next() 就等于“短路”，下游看不到
  })
}

class GreeterService extends Service {
  constructor(ctx: Context) { super(ctx, 'greeter') }
}
💡 为什么这很重要？

注意上面没有任何「注册表在启动时被 new 出来」的代码。服务是插件在挂载时占据的；一旦插件卸载，它占的 key、注册的工具、绑的监听器全部自动撤销。这就是为什么 DSH 能做到热重载，也是为什么「加功能」永远不需要改内核：你只是多插了一件家具。

事件：插件之间怎么说话

服务方法适合「直接调用」（ctx.tools.execute()）；而「拦截、观察、加策略」用事件。Cordis 有 5 种分发模式，区别只在两件事：是否 await、有没有返回值：

模式await？顺序有返回值？典型用途
emit否按注册顺序观察否纯通知（如「某事件发生了」）
waterfall否按注册顺序，环绕中间件是拦截/改写决策（审批、pre-step、tools/pre-execute）
parallel是所有监听器并行否并行扇出
serial是按注册顺序，串行是按序执行（如 turn-stopping）
bail否按注册顺序，遇到返回 bail 值就停是「谁先给答案听谁的」

waterfall：最像「洋葱」的事件

waterfall 是 DSH 里最常用、也最容易写错的一种。每个监听器收到 (...args, next)：

监听器 A改个字段，调用 next()
→
监听器 B调用 next()
→
监听器 C直接返回结果（短路）
A、B 是「协作型」监听器：改共享对象后必须 next() 把控制权交下去；C 拥有最终决策权，直接返回即可，下游不再执行。
⚠️ 最常见的 bug

写 waterfall 监听器却忘了调用 next()，就等于无意中短路了整条链——后面的审批、沙箱、日志全都不会运行。DSH 的仓库约定里专门写了一条：waterfall 监听器必须调用 next() 才能委托。

能力 seam：Cordis 之上的一层约定

「一切皆插件」再往前一步，就是 能力 seam（接缝）。一个 seam 永远是三个角色一起设计的：

📜Service Definition
声明接口：一个拥有 ctx.<key> 的 Cordis Service（抽象类或具体注册表）。
🔌Service Provider
实现它：本地、沙箱、远程、SSH 版本可以互换。
👤Consumer
使用它：通常是面向模型的工具。

规范范例是 shell：dsh-shell 定义 ctx.shell，dsh-bash-local / dsh-bash-sandbox 是两种实现，dsh-tool-bash 是消费者。于是把文件系统与进程提供方一起指向远程沙箱，Bash、PTY、LSP 就全都跟着搬过去了，不需要为每个工具写特例。这是 DSH 架构里最优雅的一点。

🧪 小测验
一个 waterfall 监听器如果没有调用 next() 就返回了，会发生什么？
答案：B。waterfall 是「环绕中间件」：只有调用 next() 才把控制权交给下游。故意短路是合法的（策略监听器拥有决策权时），但忘了 next() 往往是无意 bug。
🧪 小测验
「注册是可逆副作用」最直接的好处是什么？
答案：B。每个注册都返回（或由 effect 管理）一个 disposer，teardown 时按序释放。这让热重载、按 agent 清理、失败回滚都变得干净可靠。
