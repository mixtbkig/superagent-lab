持久化与恢复

日志再漂亮，进程一关就没了。怎么把「仅追加日志」安全地落到磁盘？崩在半夜怎么办？模型做了一半、进程被 kill，第二天怎么接着干？这一章讲 DSH 的 持久化 seam：句柄、flush 屏障、崩溃修复，以及让旧日志还能读的格式迁移。

🎯 学完这一章，你会明白
  • SessionPersistence 与 SessionHandle（read/append/flush/close）；
  • 「append 不保证落盘，flush 才保证」的语义；
  • 崩溃后如何从「有 turn/start 无 turn/end」的日志里恢复；
  • 为什么已提交的日志代次永不被移动、覆盖或删除。
🧸 小学生版：存折与「盖章」

你往存折上一笔笔写记录，但写完不等于银行系统已经记账——要柜员盖章（flush）才算真正生效。如果写到一半停电了，最后一行可能只写了一半（「撕裂的尾巴」），银行会把它撕掉，只认完整的记录。

更好的比喻是写长篇小说：你一直往后写（append），但只有点了「保存」（flush）才真正存盘；停电后重开，编辑器会告诉你「最后一段损坏，已丢弃」，前面的章回完好。

句柄：通往已存会话的唯一通道

持久化 seam 是抽象服务 ctx.sessionPersistence：在现有 SessionEvent 上暴露 create / open / stat / list / export——没有另起一套持久化事件类型。create 和 open 返回一个逐会话的 SessionHandle：

方法语义
read(offset, length)读取合法连续逻辑日志的一段；绝不返回撕裂的物理尾巴，同一句柄重复读不会看到更旧的状态
append(events)追加连续批次（首个 seq 必须等于已存 next-seq）。resolve 只表示被接受、有序、对本后端可见；不保证崩溃后还在。
flush()持久性屏障：resolve 后，所有已确认 append 都durable，且会话对其他进程物化可见。这是唯一承诺「能扛住崩溃」的操作。
close()释放句柄；写句柄会完成待处理持久化并释放写所有权。幂等、不可取消。
💡 「单写者所有权」

句柄是单所有者状态，不是共享服务。已有活跃写持有者时，第二次 open(id,'write') 会以 SessionAlreadyOwnedError 拒绝。所以恢复修复只会在「写所有权之下」发生，绝不会和活跃轮次赛跑。

flush 检查点：同步通知，异步落盘

session/event同步通知
→
有界 write-behind 窗口批量攒一攒
→
写句柄 append窗口到期触发
→
session/flush取消等待、排空至停稳
append 不阻塞生产方；loop 用 session/flush 作为「领取下一个普通轮次之前」的顺序与错误观察检查点。

后台写被拒时会按序保留对应事件、暂停自动路径、通过 logger 报告；下一次显式 flush 会重试并向调用方响亮地拒绝。session/disposed 会做同样的最终排空并关闭句柄——所以正常关闭不会丢数据。

崩溃恢复：把「半个轮次」补完整

假设进程在轮次中途被 kill，磁盘上的日志以「打开的 turn/start 而无 turn/end」结尾。持久化层不会截断或修复它（长任务里单个轮次可能非常庞大，这些事件在崩溃前已持久追加）。它返回物理上有效的连续日志，只丢弃「撕裂尾巴」里不完整的碎片。

修复是读方的职责：resume（agent-loop）通过写句柄读取已存日志，计算 interruptedTurnClosers，再作为普通批次追加：

🔧 崩溃恢复流程
① 发现中断
② 丢弃碎片
③ 计算 closers
④ 安全补写
⑤ 继续运行

只读观察方（session-query）只在内存里做同样的配平，不回写任何东西——它没有写所有权。

格式演进：旧日志也读得懂

DSH 在快速迭代，日志格式会升级（v0 → v1 → v2 → v3 …）。规则极其保守：

  • 只有「现有判别标签无法阻止不安全解释」时才 bump SESSION_FORMAT_VERSION；
  • 已提交的代次路径绝不重命名、替换或删除；
  • 每个相邻迁移包只负责一个 vN → vN+1 步骤；
  • 写 open 会先编码、校验，再在未改变源的旁边排他发布最终版本命名的后继；
  • 拒绝未来版本，而不是猜测着读。
⚠️ 为什么这么保守？

因为会话日志是用户的真实工作记录。一次错误的「迁移」可能永久损坏历史。宁可写一份新代次、保留旧代次，也绝不覆盖。这条原则也解释了为什么有 session-format-v0-to-v1、v1-to-v2、v2-to-v3、v3-to-v4 这样一串「相邻迁移包」，而不是一个大而全的转换器。

🧪 小测验
append() 成功返回，是否意味着数据已经能在崩溃后存活？
答案：B。append 的 resolve 只表示被接受、有序、对本后端可见；flush 是唯一的持久性屏障。
🧪 小测验
崩溃后，谁负责把「半个轮次」补完整？
答案：B。持久化返回物理有效日志，不截断；修复由读方在写所有权下追加缺失的工具错误、step/end 与合成的 turn/end{interrupted}。
