工具系统（下）：执行流水线

模型说「调用 bash 跑 npm test」。从这句话到真正 spawn 一个进程，中间要过八九道关卡：记录、展示、前置钩子、单调守卫、审批、沙箱、执行、文件闸门、后置策略、最终通知。这就是 DSH 的受保护执行流水线——安全与可观测性都藏在这里。

🎯 学完这一章，你会明白
  • 一次工具调用经过的完整流水线，以及每个 waterfall 能做什么；
  • 「单调守卫」和「审批」的区别，为什么审批要 fail-closed；
  • 沙箱三种模式，以及 ConfinedArgv 与「命令没跑」vs「命令被拦」的区分；
  • 并发分区、有界滚动池、取消与结果归因。
🧸 小学生版：机场安检 + 海关

你想带一件「工具」上飞机：

  • 先登记（tool/call 先写日志）：哪怕你后来没登机，也知道你带过什么。
  • 过安检（pre-execute + 守卫）：违禁品直接拦下；有些东西要看情况（单调守卫可 deny 或放行）。
  • 拿批文（approval）：危险物品要人工签字，没人签就一律拒绝（fail-closed）。
  • 走海关通道（沙箱）：告诉你只能带进「工作区」这个范围，超出就拦。
  • 回来后复查（post-execute / finalize）：检查你带回来的东西，必要时替换或加备注。

💡 为什么把「记录」放在「执行」之前？

因为 tool/call 一旦写下，即使执行中途进程崩溃，恢复时也能知道「曾计划调用什么、结果缺失」。恢复路径会把缺失的工具结果补成错误（第 12 章）。如果反过来「先执行再记录」，崩溃就会留下一个「做过但没记录」的黑洞——违反「模型可见 ⟺ 已记录」。

沙箱：把进程关进「文件效果」的笼子

沙箱只管控一件事：这个进程能写哪些文件。它有三种模式：

模式允许典型场景
read-only只允许写必要的接收器（如 /dev/null）只读分析、评审
workspace-write工作区根目录 + 显式额外目录 + 后端承诺的临时区正常编码（默认）
danger-full-access绕过隔离，直接 spawn 原始 argv显式危险操作

只有前两种会真正调用 ctx.sandbox.confine(argv, policy, signal)，返回一个 ConfinedArgv：被包装后的 argv、后端达到的强制完整性（full/partial）、以及两种 stderr 分类签名：

🟢 denial signatures

沙箱正常工作、把受限命令拦下的特征（bwrap 的 EROFS、Landlock 的 EACCES、Seatbelt 的 EPERM）。

🔴 runner failure rules

沙箱基础设施本身在执行命令前就失败的特征。消费方要先判这个，把它当「沙箱坏了」上报，而不是「任务失败」。

⚠️ fail-closed

没有可用后端时，confine() 以 SandboxUnavailableError（SANDBOX_UNAVAILABLE）拒绝。对于受限策略，「静默地不做隔离就透传」永远不合法。这就是「宁可失败，也不偷偷放行」。

后端：Linux 用 bwrap/Landlock，macOS 用 Seatbelt，Windows 用 ACL 受限令牌。把文件系统与进程提供方一起指向远程 SSH 沙箱，Bash / PTY / LSP 就全都跟着搬过去——这就是第 2 章讲的「能力 seam」的威力。

并发：不是所有工具都能一起跑

模型可能一次返回多个工具调用。执行器按 executionMode 给它们分类，进入「有界滚动池」：

调用 AisConcurrencySafe=true
调用 Btrue
调用 Cfalse（独占）
调用 Dtrue
A、B 可并行；C 独占，必须等 A、B 停下；D 在 C 之后再并行。只有显式 true 才并行，其余（含抛异常）一律独占。并行的工具不得修改父级状态。

顺序仍按「模型给出的顺序」返回结果，即使执行是乱序完成的。取消时，尚未开始的调用会被跳过，结果里也会包含 skipped 标记——绝不静默丢弃。

两道「内容改写」钩子，别搞混

钩子何时能做什么
projectContent执行完成、后置策略之前安装执行准备好的内容（文本/图片）。策略替换仍拥有最终权威。
finalizeContent规范化之后、物质化之前（每个结果恰好一次）最后一道「仅内容」不变式；即便绕过了 post-execute 的流水线失败也会调用。必须 total、不得抛错，也不能改 isError 等其它字段。

🧪 小测验
一个工具调用在流水线中被「拒绝」或「审批被拒」时，它的工具体会怎样？
答案：B。denied 分支直接跳过工具体（tool body skipped），进入 project → post → finalize → result，把拒绝作为结果返回给模型。
🧪 小测验
为什么沙箱要区分「denial」和「runner failure」两种 stderr 签名？
答案：B。消费方先判 runner failure（命令根本没跑），再判 denial（隔离生效、拦下了）。两者不能混为一谈，否则会把「沙箱坏了」误报成「任务失败」。
