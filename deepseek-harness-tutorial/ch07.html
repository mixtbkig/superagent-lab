LLM 层：Message 与流

模型是唯一真正「不可控」的外部世界。DSH 用一层很薄的抽象把它包起来：上游是一套统一的消息词汇（Message / ContentBlock），下游是每家厂商各不相同的 HTTP/SSE 协议。中间靠一个适配器（adapter） seam 把它们翻译成统一的 StreamChunk 流。

🎯 学完这一章，你会明白
  • Message 与 ContentBlock 的七种块；
  • 原始的 StreamChunk 流式协议（7 种 chunk）；
  • 适配器必须遵守的几条铁律（usage 先于 finish、arguments 保持原始 JSON 串…）；
  • LlmFailure、重试策略、空响应、上下文溢出分别怎么处理。
🧸 小学生版：不同国家的厨房，同一张菜单

DeepSeek、OpenAI、Anthropic 的「厨房」做菜方式各不相同（HTTP 接口、流式格式都不一样）。但点菜的顾客只认一张统一菜单：一份「消息」由若干「内容块」组成。

适配器就是翻译官：把统一菜单翻译成某家厨房听得懂的订单，再把厨房边做边上菜的过程（流式 chunk）翻译回统一的「上菜顺序」。这样上层循环根本不需要知道今天用的是哪家厨房。

消息 = 内容块数组

一段对话由 Message 组成；一条消息是一个类型化内容块的数组。块的联合类型由 ContentBlockMap 派生，插件可以通过声明合并添加新块：

📝 text
普通可见文本
🧠 reasoning
思考过程（thinking），区别于可见文本
🖼️ image
一个持久图片附件
📄 file
一个持久文件附件（按路由投影为 handle 文本）
🔧 tool-call
id / name / 原始 JSON arguments
➕ tool-addition
developer 消息里，激活一个工具定义
➖ tool-removal
developer 消息里，移除当前生效的定义

工具结果不是内容块，而是一等的 ToolResultMessage（含 toolCallId、结果 content、可选 isError）。assistant 消息还会在 source 里记录生成它的 provider/model，以及可选的适配器私有回放数据。

流式协议：StreamChunk

模型不是一次性吐完整段文本，而是「边想边吐」。适配器把它规范化成一条由 7 种 chunk 构成的流：

packages/llm/llm/src/types.ts
type StreamChunk =
  | { type: 'block-start'; index; blockType }          // 某个块开始了
  | { type: 'text-delta'; index; text }                // 文本增量
  | { type: 'reasoning-delta'; index; text }           // 思考增量
  | { type: 'tool-call-delta'; index; id; name?; argumentsDelta } // 工具参数增量（原始 JSON 串）
  | { type: 'block-end'; index; block: ContentBlock }  // 块结束，携带完整组装好的块
  | { type: 'usage'; usage: TokenUsage }               // token 用量（必须在 finish 之前）
  | { type: 'finish'; reason: FinishReason; replayState? } // 终止，可带回放元数据

index 把交错的 delta 关联到所属块；block-end 直接给完整块，消费者不必自己重新拼。这是一个封闭的可辨识联合，switch 以 assertNever 结尾——新增变体会在每个必须处理它的地方触发编译错误。

点一下，看流怎么拼起来

block-start index=0 type=text text-delta index=0 "我来" text-delta index=0 "帮你看一下" text-delta index=0 " a.ts。" block-end index=0 type=text block-start index=1 type=tool-call tool-call-delta index=1 id=call_1 name=read {"path" tool-call-delta index=1 ":"a.ts"} block-end index=1 type=tool-call usage { input: 1200, output: 42 } finish reason={kind:'tool-calls'}
一条流可以同时含文本块与工具调用块；usage 一定在 finish 之前，finish 之后不再有任何分片。
💡 为什么要这么设计？

因为「流」是用户体验的关键（打字机效果、首 token 时间）。如果把流强行攒成完整消息再显示，界面会卡住好几秒。DSH 的策略是：实时侧用瞬态 chunk 推给 UI 做打字机；持久侧把精确时间线压成紧凑 stream 存进日志。两套并存，各取所需。

适配器必须遵守的几条铁律

规则含义
usage 先于 finish把两者都推迟到提供方的结束标记，避免尾部 usage-only 分片破坏顺序。
arguments 全程保持原始 JSON 串部分片段用 argumentsDelta 流式传输；若提供方给的是对象，在 block-end 重新序列化成字符串。
一次适配器调用 = 一次提供方尝试适配器禁用库内重试；重试由 agent 层开新轮次负责。
空 completion 是可重试错误没有任何内容块的终止性 stop 映射为 EMPTY_RESPONSE 错误，默认会重试。
上下文溢出只有一个规范 code两家 DeepSeek 适配器都暴露 CONTEXT_WINDOW_EXCEEDED，消费方按 code 路由，不依赖文本。
回放状态归适配器所有成功 finish 可带 ReplayEnvelope；只有同一个适配器实例才拿得到私有回放状态。

失败也要「结构化」：LlmFailure

任何抛出的失败或带内失败，都会被规范化成一个可序列化、与提供方无关的 LlmFailure：message、code、status、providerRetryAfterMs、requestId…… 这样上层可以只在 code 上做决策，而不用解析各家五花八门的错误文本。

🔁 重试策略 ResolvedRetryPolicy

normal 模式：有限 maxRetries + retryableCodes + 退避（initial/max/jitter）；always 模式：无上限但同样退避。默认不配置时重试 5 次。

🧪 小测验
在 StreamChunk 协议里，usage（token 用量）必须出现在什么位置？
答案：B。适配器约定：把 usage 和 finish 都推迟到提供方结束标记，保证 usage 永远在 finish 之前、finish 之后没有分片。
🧪 小测验
适配器为什么要「禁用库内重试」，把重试交给 agent 层？
答案：B。把一次适配器调用定义成一次尝试，让重试成为 agent 层的持久事件（assistant/attempt + 新请求），可审计、可回放。
