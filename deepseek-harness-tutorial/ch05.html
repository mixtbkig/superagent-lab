会话日志：唯一真源

DSH 里没有「对话历史」这个对象。有的只是一个只许追加、不许修改的事件日志。Session 就是这份日志；模型看到的全部历史，都是从日志里算出来的。这种设计叫事件溯源（event sourcing），是理解 DSH 一切行为的底座。

🎯 学完这一章，你会明白
  • 什么是「仅追加日志」，为什么它比「存一份消息数组」更强；
  • SessionEventMap 里定义了哪些核心事件、各自负责什么；
  • deriveMessages() 如何从日志投影出模型历史；
  • 什么是 surface、surfaceOp，以及压缩怎么「改写历史」；
  • 为什么 DSH 有一条铁律「模型可见 ⟺ 已记录」。
🧸 小学生版：只写不擦的日记本

普通程序会「更新变量」——把 old 值擦掉写 new 值。但 DSH 用的是一本只许往后写、不许擦的日记本：

  • 「今天 9:00，妈妈让我写作业」——记一笔；
  • 「9:05，我去查了字典」——记一笔；
  • 「9:10，我写错了一个字，涂掉重写」——不能真擦，而是再记一笔「第 3 行作废，改为…」。

于是任何时候你翻日记，都能从头重放出「当时到底发生了什么」；也能从任意一页「分叉」出一本新日记。这就是事件溯源的全部魔法。

日志长什么样：一条事件

每个条目都是带判别的 SessionEvent：有单调递增的 seq（就是 log.length）、time（epoch 毫秒），以及按 type 判别的 data payload。因为是真正的可辨识联合，switch (event.type) 就能直接窄化 event.data。

doc 摘录：SessionEventMap 的核心成员（完整定义见 docs/subsystems/session.zh.md）
interface SessionEventMap {
  'turn/start':  { turn: number }
  'turn/end':    { turn: number; reason: TurnEndReason }
  'step/start':  { turn: number; step: number }
  'step/end':    { turn: number; step: number }
  'user/message': UserMessage                 // 人类提示 / 注入上下文 / 目标续跑
  'developer/message': { turn; step; message: DeveloperMessage; headerSeq? }
  'system/message': { turn; step; message: SystemMessage }   // 渲染后的系统提示词
  'assistant/message': { turn; step; message; stream; usage?; interrupted? }
  'assistant/attempt': { turn; step; stream } // 失败/重试/取消、未产生可见内容的尝试
  'tool/call':   { turn; step; callId; name; arguments }
  'tool/result': { turn; step; message; error?; meta? }
  'request/header':  { header: EpochHeader; reason; startsSeries? }
  'request/context': RequestContext
  'session/end-seed': { inherited?: true }
}

除了这些核心事件（含 developer/message 等），插件还可以通过 TypeScript 声明合并往 SessionEventMap 里加自己的事件——比如压缩包加了 compaction/start|summary|end，钩子桥接加了 hook/invoked|result。这就是「一切皆插件」在持久化层的体现。

💡 为什么「仅追加」这么重要？
  • 可恢复：进程崩了，重放日志就能回到崩溃前那一刻（第 12 章）。
  • 可分叉：从某一页复制前缀，就能开一个「平行宇宙」子会话（fork，第 13 章）。
  • 可审计：每次模型调用、每个工具结果都留痕，出了事能查。
  • 多消费者：UI、SDK、遥测、持久化都从同一份日志派生，不用各自维护一份状态。

模型历史是「算」出来的：deriveMessages()

日志里既有 turn/start 这种「控制事件」，也有 user/message、assistant/message 这种「产生消息的事件」。后者叫 surface 事件。把 surface 事件按顺序取出来、投影成 Message[]，就是模型看到的历史：

SessionEvent 日志（全部）
turn/start
user/message
step/start
system/message
assistant/message
tool/call
tool/result (surface)
step/end / turn/end
→
deriveMessages()
模型历史 Message[]
🟦 system
🧑 user
🤖 assistant (tool_call)
🛠 tool result
控制事件被过滤掉；只有 surface 事件参与模型历史。回放 = 用同一组事件再算一遍。

Surface 与 surfaceOp：怎么「改写」不能改的历史

既然日志只能追加，那压缩（compaction）把一大段历史总结成一段摘要时，怎么让模型「忘掉」旧内容？答案是：再追加一条 surface 事件，用 surfaceOp 声明它遮蔽（shadow）了哪些旧事件。

💡 一句话

压缩不删除任何旧事件；它追加一条新的 user/message，带 surfaceOp: { op: 'replace', startSeq, endSeq }，把被替换的那段「盖住」。deriveMessages() 投影时跳过被遮蔽的节点，模型就只看到摘要。旧日志仍在，随时能追溯。

这也是为什么 compaction/* 事件本身不是 surface 事件（不进模型历史），而摘要必须借助一条 user/message 才能进入模型视野。

铁律：模型可见 ⟺ 已记录

⚠️ 这是 DSH 最重要的一条不变量

凡是能到达模型请求的东西，都必须能从会话日志重建。如果你想让模型看见一个新输入，就必须为它新增一种 session 事件；否则就违反了这条规则。这条规则保证了「回放 = 真实发生过的事」，也让调试、恢复、fork、遥测全部成立。

assistant/message 里为什么还藏着一整条 stream？

你可能注意到 assistant/message 除了消息本身，还带一个 stream: AssistantStreamRecord[]。这是把模型流式输出的精确时间线（每个 chunk 及其时间戳）压缩后内嵌进去，用来：

  • 回放时还原「打字机效果」与首 token 时间；
  • 遥测 / token 记账直接读紧凑记录，不用展开；
  • 失败的尝试则记为 assistant/attempt，同样内嵌 stream，但不伪造模型历史。

压缩（compaction）把长历史总结成摘要时，是怎么做到的？
答案：B。日志永不删除；摘要通过一条新的 surface 事件「盖住」旧区间，deriveMessages() 投影时跳过被遮蔽的节点。
🧪 小测验
「模型可见 ⟺ 已记录」这条规则，最主要保证了什么？
答案：C。如果某条输入能进模型却不在日志里，回放就会失真。这条不变量是整座大厦的地基。
