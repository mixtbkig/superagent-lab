工具系统（上）：注册表与 Schema

工具是 harness 真正「动手」的地方。但「注册一个工具」远不止写个函数：它要声明面向模型的 schema、要能按 agent 作用域过滤、要支持条件准入、要能并发分区。这一章讲工具的静态结构；下一章讲它怎么被执行。

🎯 学完这一章，你会明白
  • ToolDefinition 的每个字段，以及哪些字段绝不能泄漏给模型；
  • defineTool 的 schema DSL（ValueSchemaSpec）如何推导参数类型；
  • 作用域（scope）与 ToolRestriction：为什么子 agent 能看到不同的工具集；
  • 条件准入 when 与「步骤拥有的准入集合」。
🧸 小学生版：一个工具箱

每个工具就像工具箱里的一件工具，箱子上贴着三样东西：

  • 使用说明书（schema）：叫什么、干什么、需要什么参数。这是给模型看的，必须精确。
  • 安全标签（timeout / 并发 / 能否修改共享状态）：给调度器看的，模型看不到。
  • 使用权限（restriction）：哪些同学可以借这件工具。低年级同学可能只准用剪刀，不准用美工刀。

ToolDefinition：一个工具的完整档案

注册表里存的是「工具定义」，它同时包含「模型看得见的部分」和「只有宿主看得见的部分」。这两者必须严格分开——schemas() 只把 name / description / parameters 发给模型。

字段模型可见？作用
name / description / parameters✅ 是面向模型的工具 schema
output❌ 否规范输出声明：schema（原始 JSON Schema）+ render()（把值转成 ContentBlock）+ presentationMeta()
execute(args, exec)❌ 否真正干活的函数，返回规范 JSON 值
timeoutMs❌ 否协作式超时预算（由 timeout 策略包装 tools/execute 强制执行）
isConcurrencySafe(args)❌ 否纯同步分类器：返回 true 才允许与兄弟调用并行
projectContent / finalizeContent❌ 否内容投影的两个钩子（执行前准备 / 最后一道仅内容变换）
presentCall / presentResult❌ 否纯展示函数：UI 如何画「进行中 / 已完成」的卡片
⚠️ 一条硬规则

output / execute / projectContent / finalizeContent / timeoutMs / isConcurrencySafe / presentCall / presentResult 绝不能泄漏到模型请求中。schemas() 通过显式允许列表构建 ToolSchema[]。这不是洁癖，而是安全与稳定性的要求：模型不该看到你的实现细节与调度元数据。

defineTool：用 Schema DSL 写工具

第一方工具不手写校验；它们用 defineTool，由它根据 schema 推导参数类型、校验输入、推导 execute 的返回类型：

用 defineTool 注册一个「读文件」工具（示意）
export const readTool = defineTool({
  name: 'read',
  description: 'Read a file from the workspace',
  parameters: {
    path: { type: 'string', required: true },       // required: true 标记必填
    offset: { type: 'integer' },                     // 可选
    limit: { type: 'integer' },
  },
  output: {
    schema: { type: 'string' },                      // 规范返回：字符串
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute({ path, offset, limit }, exec) {     // 参数已被推导为精确类型
    return await fs.readText(path, { offset, limit, signal: exec.signal })
  },
  timeoutMs: 10_000,
  isConcurrencySafe: () => true,                     // 只读 → 可并行
  presentCall: (args) => ({ card: 'file', title: `Read ${args.path}` }),
})

参数不匹配会抛 ToolArgsError（INVALID_ARGS）；函数体或后置策略产出无效值会抛 ToolOutputError（INVALID_TOOL_OUTPUT）。两者都走常规工具错误路径，不会把整个会话搞崩。

Schema DSL 支持的节点：string / number / integer / boolean / null / array / object / json / oneOf。标量还支持 enum 与 const；对象节点必须显式声明 additionalProperties。精确推导最多到 16 层容器，之后回退为 JsonValue——这是为了防止把 TypeScript 的类型实例化栈打爆。

作用域：谁能看见哪些工具

DSH 的工具可见性只有两层，是扁平的：全局的（所有 agent 可见）或带作用域的（恰好属于一个 scope key）。约定是：一个活跃 agent 就是它自己 scope 的 key。带作用域的注册不会向下继承给 subagent；子树行为靠 lineage 数据表达，从不靠 scope 结构。

工具解析：全局层 → 作用域限制（取交集）→ 叠加作用域自身注册（可 shadow）。被委派的子 agent 会保留它回报所依赖的工具。

条件准入：这一步到底允不允许用这个工具

有些工具只在特定条件可用，比如「plan 模式下不允许写文件」。DSH 的机制是：注册时给一个 when(context) 条件；每个拟议步骤，agent-loop 以捕获的模型选择调用一次 ctx.tools.resolve()，得到一个「本步准入集合」：

interface ToolActivationContext {
  agent: Agent
  modelSelection: Readonly   // provider / model / reasoning effort
  signal: AbortSignal
}
// 注册时：
ctx.tools.register(def, { when: (c) => c.modelSelection.model !== 'some-model' })
  • 返回的 ResolvedToolSet 决定该步骤的工具声明、执行器分区、批次里每一次调用（含 PTC 子调用）。
  • 执行时 ctx.tools.executable() 会再套一层——没有集合时排除所有条件注册。
  • 同名替换或新限制会阻止「尚未开始」的调用使用已准入注册；步骤批次结束后释放集合。

工具是「可扩展的」，不是「写死的」

正因为工具只是注册表里的一条记录，DSH 的大部分「能力」都能以工具的形式出现，而不必改循环：fs 的 read/write/edit、bash、web_search、subagent、workflow、skill、todo_write、ask_user_question……统统是工具。第 18 章的全景图会列出所有第一方工具。

🧪 小测验
下面哪个字段会出现在发给模型的工具 schema 里？
答案：A。只有 name / description / parameters 会进模型请求；其余都是宿主侧元数据，绝不能泄漏。
🧪 小测验
一个 scope 的 ToolRestriction 过滤掉了全局工具 bash，那么这个 agent 调用 bash 会怎样？
答案：B。被过滤掉的全局工具「既不出现在提示词中，也拒绝执行」；scope-local 注册则在过滤之后叠加，不受影响。
