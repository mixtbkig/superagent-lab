前端、传输与多端

到现在为止我们都在讲「后厨」——模型、工具、日志、循环。但用户看到的是「前厅」：一个会打字、会画卡片、会实时更新的界面。这一章讲 DSH 如何把后厨和前厅拆开，又让同一套后厨服务 Web、Desktop、CLI、SDK、ACP 五种门店。

🎯 学完这一章，你会明白
  • Host（Node）与 Client（浏览器）如何分工，靠什么通信；
  • Typert RPC 网关与「类型图」是什么；
  • Web 的插件表（dsh.client）、__DSH_BOOT__ 与 slot 组合；
  • Desktop（Electron）、SDK（JSON-RPC）、ACP 各自怎么复用同一套核心。
🧸 小学生版：前厅与后厨

餐厅里，前厅负责点菜、上菜、摆盘（浏览器 UI）；后厨负责真正做菜（Node 里的模型、工具、会话）。中间靠一张点菜单（RPC 协议）传话。

妙的是：同一间后厨，可以同时服务堂食（Web）、外送（Desktop）、打包窗口（CLI）、机器人取餐（SDK/ACP）。门店不同，菜谱（核心）完全一样。

Host 拥有「事实」；Client 只做「呈现」。所有跨进程调用都经过统一的 RPC 网关。

Typert：让 RPC 也有类型

typert（type-graph）是 DSH 自研的「类型图」机制。它从 TypeScript 源码分析出远程方法的描述符（参数、返回、Context 声明），生成运行时注册表，让 Host 与 Client 之间的调用在编译期就有类型，而不是手写一堆 unknown 与运行时校验。

Web 的组装：插件表 + 启动图 + Slot

五种门店，同一后厨

形态怎么跑关键点
Webdsh web：Node HTTP 服务器 + 浏览器 client 插件默认 loopback（127.0.0.1），可用 --host 暴露；SSE 流 + RPC
DesktopElectron 启动私有 Desktop Host，调用共享 CLI 与完整 Web 应用窗口用 file:// 加载已构建资源，经 Node IPC 桥接 fetch；不走本机 HTTP 服务器
CLI / headlessdsh --profile headless "task"一次性运行器，无服务器；适合 CI / 脚本
SDK进程外 JSON-RPC over stdioTypeScript 客户端 + Python 运行时 wheel；即 --profile sdk
ACPAgent Client Protocol 服务器（JSON-RPC stdio）仅面向自动化；给支持 ACP 的编辑器/工具驱动
💡 为什么 Desktop 不用 HTTP 服务器？

因为 Electron 可以直接用 file:// 加载打包好的前端，再通过 Node IPC 把 fetch 请求桥接到私有 Host。这避免了在本机开一个监听端口，减少了攻击面，也省了端口冲突的麻烦。Web 与 Desktop 共享产品数据，但包、启用选择与锁文件保持独立。

Conversation：把「事件」变成「卡片」

浏览器收到的不是「HTML」，而是一条条 SessionEventLikeEntry（持久事件，或实时的 assistant/live-chunk 瞬态事件）。ui-conversation 把它们折叠成 Chat 节点：

  • Event Definition：业务包一次匹配一个事件（或瞬态事件），按稳定 (kind, id) 折叠成确定性 State，可选地物化成一个节点。
  • Group Definition：从物化后的节点派生「组」（如一个 workflow 运行的所有阶段）。
  • View：Chat / Trajectory 等 target 只读自己的 snapshot，渲染 target 自有节点。

这套设计的关键是可回放：历史分页与实时流走同一套匹配/更新接口，所以「刷新页面」和「一直开着」看到的是同一个东西。

🧪 小测验
在 Web 形态里，谁拥有「事实」（会话、工具、模型调用）？
答案：B。Host 拥有事实，Client 只做呈现；所有跨进程调用经 Typert RPC。
🧪 小测验
为什么 Desktop 应用不像 Web 那样启动一个本机 HTTP 服务器？
答案：B。Electron 用 file:// 加载前端并经 IPC 桥接 fetch；Web 形态才用 node:http 服务器。
