系统提示词与上下文

模型每次请求都「失忆」，所以 harness 必须在每次请求前，把它该知道的一切重新喂一遍：身份、规则、可用工具、工作区文件、当前时间……这些内容怎么拼、按什么顺序、什么时候刷新，就是本章的主题。

🎯 学完这一章，你会明白
  • PromptSection / PromptContext / AssembleContext 三者的分工；
  • 提示词如何按 order 排序、插值，最终变成 system/message（surface 第 0 号节点）；
  • 动态上下文（AGENTS.md、时间、文件引用、skill 目录）如何作为 user-role 快照注入；
  • 为什么系统提示词不算「请求字段」，而是「派生历史」。
🧸 小学生版：开学第一天的资料包

新老师每次上课都「不认识这个班」。于是每节课前，班长要递上一叠资料：

  • 班级公约（系统提示词）：我们是谁、要遵守什么规则、有哪些工具可以用。相对稳定，每节课都递。
  • 今日课表（动态上下文）：今天几号、天气如何、临时通知。变化时才重新递一份，否则沿用。

DSH 把这两类严格分开：前者是「提示词段落」，后者是「动态上下文」，各自有各自的刷新规则。

三样东西

概念是什么关键字段
PromptSection系统提示词的一段name、order、text（静态或函数）、interpolate、complete
PromptContext动态模型上下文，会作为 user-role 快照落盘name、order、text、interpolate、required
AssembleContext一次组装的作用域层与控制信号scope、signal，以及 agent 扩展的 agent / modelSelection

最终渲染出的文本，被 agent-loop 作为 system/message 提交——第一个步骤作为 surface 第 0 号节点追加。

排序规则：段落先按 order 升序，再按名称的代码单元顺序。仓库贡献方通过 getSectionOrder() 解析具名分配，而不是自己乱写数字（比如 TOOL_APPLY_PATCH 是 1350，夹在 TOOL_EDIT 1300 与 TOOL_GLOB 1400 之间）。

插值：text 里可以写 {{variable}}，默认由 renderPrompt 插值；若 interpolate: false 则原样保留（这对「目录名恰好长得像变量」的情况很重要）。

complete：如果一个片段声明 complete: true，它会被当作完整提示词——组装仍会跑协作 waterfall（让工具、上下文、变量解析），最后把这个片段恢复成唯一的提示词段落。多个有效的 complete 段会让组装失败。

💡 一个反直觉的设计：系统提示词不是「请求字段」

在很多 harness 里，system prompt 是请求里的一个 system 字段。但 DSH 把它当作派生历史：渲染后作为 system/message 事件写在 surface 第 0 号节点上。这样：

  • 提示词变化 = 追加或替换一个 system 节点，而请求头（request/header）保持不变；
  • 回放时从日志就能重建「当时模型到底看到了什么提示词」；
  • 压缩可以把旧的系统节点一起处理，而不会破坏「请求是日志的纯函数」。

动态上下文：变化时才刷新

PromptContext 是「会变的上下文」，比如当前时间、工作区文件清单、可用技能目录。它不是每步都重发，而是：

  • 组装时解析并排序；
  • agent-loop 只在完整快照发生变化、或被压缩移除时，才把它记录在保留的模型历史之后；
  • 记录形式是持久的 user/message 快照（带来源），所以回放时也能重建。

为什么用 user-role 消息而不是系统提示词？因为快照会随会话演进多次出现，塞进 system 字段会污染「请求头」，也会让「请求 = 日志纯函数」失效。作为普通消息，它天然支持追加与遮蔽。

上下文家族：谁在往提示词里塞东西

包注入什么
context/agent-instructions工作区里的 AGENTS.md / CLAUDE.md 指令文件（含子目录）
context/time-context当前时间 / 时区
context/file-reference用户用 @文件 引用时，把文件内容或摘要注入
context/session-reference跨会话引用（从另一个会话摘录材料）

注意 agent-instructions 就是一个很好的例子：它读取工作区的 AGENTS.md，把里面的规则变成模型可见的上下文——你今天读到的很多「工作方式约定」，本身就是通过这条链路进入模型的。

消息来源与 ContextForm：语义，不是外观

每条注入的上下文都带一个 MessageSource（谁产生的）和一个可选的 form（这是什么类型的信息）。form 的取值是语义的，不是视觉的：

instructions
从工作区文件读出的、模型应遵守的指令
catalog
本会话可用项目的目录，随变化重新发布
snapshot
当前状态；同一生产者的后一份会取代前一份
notice
一次性事件通报，不取代任何东西
relay
另一个 agent 发来的消息
recall
从别的会话日志里摘录的材料

为什么这么细分？因为 UI 需要知道「这条该画成折叠的指令、还是可刷新的目录、还是一次性通知」。语义归生产者，外观归消费者——这是 DSH 反复出现的分工原则。

🧪 小测验
渲染后的系统提示词在 DSH 里以什么形式存在？
答案：B。系统提示词是派生历史的一部分，以 system/message 事件写在 surface 第 0 号节点，因此提示词变化不会改变 request/header。
🧪 小测验
为什么动态上下文（如时间、文件清单）做成 user-role 快照，而不是塞进系统提示词？
答案：B。快照会随会话演进多次出现；作为消息可追加、可被压缩遮蔽，且保持「请求 = 日志的纯函数」。
