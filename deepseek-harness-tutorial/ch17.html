安全、可观测与工程约束

一个能让模型读写文件、跑命令的框架，如果安全与工程质量不过关，就是灾难。DSH 把这些「看不见的地基」也当成一等公民：多道安全闸门、完整的遥测链路，以及一套近乎苛刻的源码门禁。

🎯 学完这一章，你会明白
  • 安全的三道闸门：沙箱、审批、守卫（guard）；
  • 「防御性编程」清单里最关键的几条；
  • 可观测性：OTel、会话遥测、产品遥测、token 计量；
  • 为什么 DSH 对测试、类型、文档的要求这么高。
🧸 小学生版：工厂的安全规程 + 监控 + 质检
  • 安全规程：危险机器要有护栏（沙箱）、要家长签字（审批）、不许连轴转（守卫）。
  • 监控摄像头：每个车间都装摄像头，出问题能回放（遥测 / 日志）。
  • 质检：每件产品出厂前都要过检查（测试 / 类型 / 文档门禁）。

安全：三道闸门

🧱 沙箱 ctx.sandbox
把子进程 argv 包进「文件效果」策略：read-only / workspace-write / danger-full-access。没有后端就 fail-closed。
✍️ 审批 ctx.approval
危险操作前一次性授权；缺失应答者即拒绝。审计事件仅日志。
⏱️ 守卫 guard
repeat-tool-reminder（重复调用提醒，建议性）+ timeout-policy（tools/execute 截止时间强制执行）。
⚠️ 安全设计的三个关键词
  • fail-closed（失败即关闭）：拿不准就拒绝，绝不「偷偷放行」。
  • 显式 > 隐式：默认值必须在拥有它的实现里作为一个显式的 resolve(request): Spec 步骤，不能藏在 run() 的 ?? default 里。
  • 不可静默透传：受限策略下，无隔离透传永远不合法。

防御性编程：源码里的「交通规则」

DSH 有一份专门的 docs/defensive-patterns/，按 artifact 分类列出评审时必须遵守的规则。几条最能代表其精神的：

规则含义
Switch 判别标签闭合联合以 assertNever 结尾；可合并扩展的联合走文档化 default。不要链式 if。
Waterfall 必须 next()不调用 next() 就短路整条链——大多数是 bug。
品牌化跨边界 IDSessionId、ToolCallId、JobId 不能互换，用 Branded<B>。
不新增 as unknown保持或降低既有基线；用类型化值或校验替代。
空 catch 要命名错误说明为什么吞掉它，且 try 只包一条语句。
错误要结构化类型化、可本地化、可行动的失败报告；明确处理归属与失败保证。
模型可见 ⟺ 已记录老规矩，但也是安全与可审计的根基。

可观测性：三条遥测线

otel共享 Cordis OTel 上报通道
·
session-telemetry对外会话上报（脱敏 waterfall）
·
product-telemetry显式产品分析事件，OTLP/HTTP
·
session-log-deepseekDeepSeek 会话日志贡献器

配合 token-meter（可回放 token 计量）与 session-query（会话检索 / 全文搜索），你可以回答「这轮花了多少 token」「为什么这次请求慢了」「某个工具多久没成功过」这类问题。

🔒 脱敏是默认

会话上报有一条 session-telemetry/record 脱敏 waterfall，所有记录在离开进程前都会经过它。默认策略是 FEEDBACK_ONLY——只有你显式给出反馈（点赞/点踩/编辑/撤回）时，才释放到该事件为止的完整规范会话日志前缀。

工程约束：为什么这么「卷」

DSH 的 AGENTS.md 与 docs/testing.md 里有一套近乎苛刻的门禁。举几个例子：

strict: true
所有代码在 strict + noImplicitAny 下编译；每个残留的 any 都要说明为什么无法窄化。
每文件 100% 覆盖
test:coverage 是 CI 覆盖门禁（不是 test）：packages/*/*/src 逐文件 100%。
快照回放
每个非平凡的模型/用户可见改动，都要更新一个无秘钥的录制会话快照。
文档同步门禁
doc-sync：类型等价、链接、字数预算、生成目录的新鲜度，全部机器校验。
源码面 vs 产物面
静态门禁走 tsconfig paths 指向 src；消费构建产物 lib/ 的门禁必须显式声明依赖。
双 SDK 投影
agent-loop / session / SessionEventMap 的改动要同时更新 TypeScript 与 Python SDK 的期望输出。
💡 这给我们学习者的启示

读 DSH 源码时，你会发现它「写得慢、写得稳」：每个类型都有 JSDoc 契约，每个行为都有测试，每个决策都有 Agent Note 记录「为什么这样、放弃了什么、怎么验证」。这本身就是一份极好的软件工程教材——建议你顺手翻翻 .agents/notes/ 里的决策记录，比读代码更能理解设计取舍。

🧪 小测验
「fail-closed」在审批场景指什么？
答案：B。缺失、不负责、抛异常都产生 unavailable，调用方只接受 allowed-once，其余一律拒绝。
🧪 小测验
DSH 的 CI 覆盖门禁是哪个命令，要求是什么？
答案：B。test:coverage 才是 CI 覆盖门禁（不是 test），要求逐文件 100%。
