轮次与步骤：生命周期

第 1 章给了循环的骨架，第 4 章给了事件的顺序。这一章我们钻进 agent-loop 这个包，看一个 Agent 从「被创建」到「被销毁」的完整生命周期：谁拥有它、谁能拦它、取消到底取消什么、失败怎么重试。

🎯 学完这一章，你会明白
  • AgentHandle、Agent 接口与 setup 创建窗口；
  • send / followup / steer / inject / cancel 分别把消息送到哪里；
  • agent/pre-step 的 reject / enter 决策，以及它为什么是唯一的请求推导前钩子；
  • 请求失败后 agent/request-error 如何决定重试；
  • 取消（cancellation）与中断恢复的精确语义。
🧸 小学生版：一个学生的「一节课」

Agent 像一名学生，Turn（轮次）像一节课：上课铃响（turn/start），老师发任务，学生做若干道题（steps），下课铃响（turn/end）。

  • setup：学生入学注册（分班、领课本），注册完才正式「出现在名单上」（agent/created）。
  • pre-step：每道题发下来前，班长可以先看一眼，决定「这题不做了」（reject）或「换成这两道」（enter）。
  • cancel：老师说「停」，学生立刻停下当前动作；停之前已经写进作业本（日志）的，不会擦掉。
  • request-error：某题做错了，可以申请「重做一次」，而不是直接判零分。

Agent 的所有权：AgentHandle

创建/恢复一个 agent 时，返回的不是裸的 Agent，而是一个带 disposer 的句柄：

packages/core/agent/src/index.ts
interface AgentHandle {
  agent: Agent
  dispose(): Promise   // 停止循环、等待退出、注销、移出 store、最后展开作用域世界
}

这个 disposer 是一个能力（capability）：只有持有它的消费者才能把 agent 拆掉。注意 ctx.agents.get(id) 返回的是裸 Agent，拿不到 dispose——这就是「所有权」的体现。配置创建的 agent（循环自己的启动）由循环的 fiber 拥有，连句柄都不需要。

💡 两种 Agent 视角
  • Agent（句柄）：UI、hook、编排器面向的活动对象，提供 send / inject / steer / cancel / whenIdle。
  • AgentHandle（所有权）：谁造的谁持有，负责最终 teardown。

它们的共性是：日志才是真源。agent.session 拿到的 Session，就是那份仅追加日志。

setup 窗口：注册的黄金时刻

创建 agent 时有一个 setup 回调，它在「Session 已入库、session/created 已发、但 Agent 还没注册、agent/created 还没触发」的窗口里运行：

new Session
→
session/created
→
setup(agentCtx, agent)可注册专属工具/提示词
→
agent/created
→
首次组装提示词
在 setup 里通过 agentCtx 注册的东西，会在第一次组装前就存在，且随 agent 销毁一起回收。

setup 可以返回一个「发布前一刻」调用的同步 commit；如果 setup 拒绝、commit 抛错、或所有者 dispose，整个事务回滚、Session 被移除——但恢复出来的待处理输入与已存事件会保留。

消息怎么进到 Agent 里：四个入口

方法送到哪会不会唤醒 driver典型用途
send(msg, target, wakeup)指定的 inbox 边界可控制底层统一入口
followup(msg)下一轮（next-turn）是用户正常发消息
steer(msg)下一步（next-step）是运行中插话「顺便也改一下 b.ts」
inject(msg)下一次获准的请求否注入上下文（文件变更通知、skill 目录、定时提醒）

核心区别：followup 开新轮次，steer 插进当前轮次的下一步，inject 只挂上下文不唤醒。所有输入都走同一个 inbox；注入的上下文要等一条唤醒消息才真正被处理。

pre-step：唯一的请求推导前钩子

在真正组装请求之前，agent/pre-step 瀑布会拿到「本步要进入的完整消息批次」，并返回一个决策：

type PreStepDecision =
  | { kind: 'reject' }                                  // 不进入这一步
  | { kind: 'enter'; messages: UserMessage[]
      startsRequestSeries?: true }                       // 进入，并给出要追加的消息批次
  • reject：不打开步骤。若这是本轮的首次领取，则关闭一个「没有步骤」的轮次。
  • enter：给出 step/start 后要追加的完整消息批次。决策里省略的已领取消息保持删除状态；领取后新插入的输入留待后续。

它是「请求推导前唯一的 waterfall」——也就是说，这是你最后一次能改变「这一步到底发什么给模型」的机会（除了请求失败后的 agent/request-error）。压缩、技能目录注入、计划模式追加，都挂在这里。

失败与重试：request-error

模型请求失败写 assistant/attempt
→
agent/request-error监听器可修复并返回 retry
→
重试：同一已渲染组装不重复 pre-step / 用户准入
默认返回 undefined 就让失败成为终态；返回 { kind: 'retry' } 且不调用 next() 才接管恢复。

重要细节：重试不会重复 pre-step、也不会重复接纳用户消息。它只在「仍打开的步骤内」重新准备调用、复用已冻结的渲染组装。只有剪枝或摘要推进了 surface 替换代次时，重试才有意义；否则仍以原始错误为准。

取消与「欠下的工作」

cancel(cause, options) 会清空排队与 steering 工作（除非 keepInbox），并中止当前轮次或轮次间任务。规则是：

  • 同一个活动，第一个原因生效；没有活动时取消是 no-op，也不会「武装」后续工作。
  • 取消中已经提交到日志的内容不撤销；未派发的工具调用不会出现。
  • 如果进程在「结算（settlement）之前」硬中断，会留下一个打开的 turn/start 而无 turn/end——恢复时由 agent-loop 计算出 interruptedTurnClosers（缺失的工具错误、未闭合的 step/end、合成的 turn/end{kind:'interrupted'}）补上（第 12 章）。

🧩 设计动机

为什么把循环放在 agent-loop 这个「可替换的插件」里，而不是写死在核心？因为不同的产品形态（交互式编码、无人值守批处理、子代理、Ralph 循环）可能需要不同的驱动策略。核心只规定 Agent 接口与事件词汇，循环怎么转由插件决定。扩展插件只依赖 agent，绝不直接依赖 agent-loop——所以循环始终保持可替换。
