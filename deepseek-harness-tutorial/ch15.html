人在环路：审批、计划、目标与任务

一个能自己动手的智能体，必须随时可以被人类叫停、纠正、授权。DSH 把「人」也设计成了系统里的一等公民：审批、权限预设、计划模式、提问、目标、定时提醒、后台任务——它们共同构成「human-in-the-loop」的外围治理层。

🎯 学完这一章，你会明白
  • 审批（approval）为什么必须 fail-closed，ask / never 两种策略的区别；
  • 权限预设、计划模式、ask_user_question 各自的定位；
  • 目标（goal）如何跨轮次持续，Goal Round 与 activation 的含义；
  • 定时提醒（schedule）、后台任务（jobs）、待办（todo）、交付物（deliverables）。
🧸 小学生版：家长签字、请假条、许愿清单、闹钟
  • 审批：动危险东西前要家长签字，没人签就不许动（fail-closed）。
  • 权限预设：家长先定好「今天允许做什么」的档位。
  • 计划模式：先交一份计划书给家长审，批了才开工。
  • 提问：遇到不会的，举手问老师（ask_user_question）。
  • 目标：本子上写着「这学期要考 100 分」，跨很多天才完成。
  • 闹钟：到点提醒你（schedule）；后台任务：一边烧水一边写作业（jobs）。

审批：这个操作能不能继续？

ctx.approval 只回答一个问题：「这个具体操作是否可以继续？」它的结果是一个闭合的联合，失败即拒绝：

allowed-once
只授权「所询问的那一次」操作
rejected
明确拒绝
cancelled
请求被撤回
unavailable
没有应答者 / 不负责 / 抛异常 → 一律当拒绝

每个请求都会得到一个全新的 ApprovalRequestId，并配对写入两条仅日志审计事件：approval/asked 与 approval/decided。按会话策略 ApprovalPolicy 决定分发前发生什么：

策略行为场景
ask（默认）委托给组合的应答者链；没有应答者则 fail-closed 为 unavailable交互式使用
never永不问人，每次询问确定性地返回 rejectedCI、无人值守
⚠️ fail-closed 的意义

缺失、不负责、抛异常或不合规的应答者，都产生 unavailable，而不是放行。调用方（tools、tool-bash）只接受 allowed-once，其余一律拒绝。这正是「宁可挡住，也不误放」。

权限预设与计划模式

🎚️ 权限预设 permission-presets

一组具名的「权限档位」（PresetSpec/PresetOption），派生出一个 custom 状态。切换记录为仅日志的 permission/preset 事件。UI 上体现为「新会话默认档」与当前会话的 /permission 弹窗。

📋 计划模式 ctx.planMode

只记日志的 plan/mode 状态；在 agent/pre-step 追加/冲刷待定选择；提供 exit_plan_mode 工具与 /plan 命令，形成「先出计划、经审阅再退出计划模式」的闭环。

计划模式和权限预设经常一起用：先 plan（只读探索、产出计划）→ 人审 → 退出 plan 并提升权限 → 真正执行。这就是「先看图纸再动工」。

提问：ask_user_question

模型遇到歧义时，可以调用 ask_user_question 工具，向 UI 发起一个人工问答请求（AskUserQuestionRequest，带选项、多选、描述）。这是 UI 支持的人工问答 seam：没有 UI 应答者时，它按约定的错误分类处理，而不是卡死。

目标：跨轮次的「许愿清单」

Goal 是附着在现有会话上的单个持久完成目标，带按修订号演进的阶段：

active进行中
⇄
paused暂停
⇄
blocked因问题停止（带 code + 说明）
→
complete完成
每次获准的持久变更都会递增 revision；状态存在 goal/change 会话事件里，日志仍是真源。

关键概念是 Goal Round：为当前目标接纳的一次续行周期，具体化为一个由目标触发的轮次（可含零到多个步骤）。同一会话里无关的人类轮次不消耗 Goal Round 上限。

💡 activation：进程本地、不参与回放

目标还有一种进程本地的激活态 armed / disarmed，有意不参与持久回放。因此恢复或 fork 之后，自动工作不会自己开始——必须由人再授权一次（/goal 或模型工具）才会 re-arm。这是一个安全阀。

定时提醒、后台任务、待办、交付物

子系统是什么关键点
scheduleHost 拥有的持久提醒，可投递到现有或新会话到点触发一条唤醒消息；支持一次 / 周期
jobs后台任务运行时（如长跑的 bash）JobId 品牌化；job/registered + job/settled；job_* 工具读/停；输出环
todo面向模型的 todo_write 工具整列表条目；持久事件所有权 + 投影；UI 上就是待办清单
deliverables一轮交给用户的东西present 声明的 PresentedFile + 由 git 快照得出的 WorkspaceChangesSummary
🔔 一个常见组合

「先 schedule 一个明早 9 点的提醒 → 到点唤醒会话 → agent 用 jobs 起一个长跑测试 → 用 todo 记录进度 → 最后用 present 把改了哪些文件交付给你」。这些子系统各管一段，但都挂在同一条会话日志上，所以随时可回放、可审计。

🧪 小测验
审批的应答者「不存在 / 抛异常」时，结果是什么？
答案：B。缺失/不负责/抛异常都产生 unavailable，调用方只接受 allowed-once，其余都当拒绝。
🧪 小测验
目标（goal）的 activation 为什么有意不参与持久回放？
答案：B。activation 是进程本地状态；恢复后自动续跑需要一次经人类授权的 re-arm，避免「睡一觉醒来它自己干活」。
