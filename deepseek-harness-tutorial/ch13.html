子代理与多智能体编排

一个 agent 再强，也有「上下文装不下、任务太多、需要并行」的时候。DSH 的解法是：把工作委派出去。委派可以给一个全新的子 agent（spawn）、一个继承父对话的子 agent（fork）、甚至一个真正的 Claude Code / Codex 会话。再往上，还有 workflow 脚本与 Agent Teams 两种编排层。

🎯 学完这一章，你会明白
  • subagent seam：startActivation、能力标记、parent vs caller 交付；
  • spawn / fork / 外部后端（Claude Code、Codex、ACP、SDK）的区别；
  • workflow：模型写的 JS 脚本如何扇出到多个子 agent；
  • Agent Teams：持久 roster、共享任务 DAG、peer 直连消息；
  • lineage（父子关系）为什么只作数据、不影响可见性。
🧸 小学生版：项目经理与外包团队

你是项目经理（主 agent）。手头活太多，你可以：

  • spawn（招新人）：招一个全新实习生，只给他任务说明，不知道项目前情。
  • fork（复制自己的脑子）：把自己的会议记录复印一份给实习生，让他接着你的思路干——但之后各干各的。
  • 外包（外部后端）：把活交给隔壁公司的 Claude Code / Codex 团队，他们用自己的流程，只把最终报告交回来。
  • workflow（流水线）：写一张「先做 A，再把 A 的结果拆给 B、C 并行」的作业单，让系统自动调度。

subagent seam：一套统一的委派接口

所有后端共用 startActivation。能力标记（SubagentCapabilities）会在启动前校验请求选项：agentOptions、agentPreset、outputSchema、depthLimit。prepareContinuable 选择「本地 Agent 创建」，start 选择「一次外部执行」。

概念含义
SubagentStartRequestcwd、prompt、parent、signal、可选 agentOptions / outputSchema / maxDepth / agentPreset
delivery: 'parent' | 'caller'parent：完成后通知模型（注入消息）；caller：只把结果返回给调用方（不打扰父对话）
SubagentResult最终文本、可选 structured（按 outputSchema）、诊断、状态
continuable本地子 agent 拥有持久 Session，最多一个在线 activation；不在线时可冷恢复、发消息继续

五种后端，各有分工

提供方怎么跑何时选它
subagent / spawn-in-process同进程新建一个全新子 agent（不带父历史）任务独立、需要干净上下文
fork-in-process从父会话某一点 fork，继承前缀历史子任务需要理解父对话上下文

subagent-codex通过官方 app-server 协议跑一个隔离的 Codex 线程需要在父工作区里跑真实 Codex

💡 关键设计：能力与运行时拆分

本地子 agent 在启动时就确定能力（preset、输出 schema、深度上限），运行时再单独管理输入准入、冷恢复、先子后父的释放顺序。activation 结果在资源释放和完成通知之后才结算——所以「拿到结果」意味着「一切都清理干净了」。

lineage：父子关系只是「数据」

子 agent 与父 agent 的关系（parentSession、delegationDepth、运行时 subagentDepth）以数据形式携带，从不影响可见性。带作用域的注册不会向下继承给子 agent；子树行为靠 lineage 数据表达，从不靠 scope 结构。这是一个很克制的设计：它让「谁能看到什么」保持扁平、可预测。

主 Agentscope A
↓ 委派
子 Agent 1scope B · depth 1
子 Agent 2scope C · depth 1
↓ 再委派
孙 Agentscope D · depth 2
每个 agent 是自己的 scope key；lineage 记录「谁是谁的孩子」，但子 agent 的工具可见性由自己的 scope + restriction 决定，不自动继承父的 scope 注册。

workflow：让模型写「编排脚本」

当任务复杂到需要「先 A，再把 A 拆给 B、C 并行，最后汇总」，逐个调用 subagent 工具会很啰嗦。workflow 允许模型写一段 JS 脚本，脚本里调用 agent()、parallel()、pipeline() 等钩子，由引擎在沙箱运行时里执行：

传给 workflow 引擎的脚本（示意；真实有 meta/args 与结果校验）
// meta: { name: 'review-fanout', description: '并行审查多个文件' }
const files = args.files
const results = await parallel(
  files.map(f => () => agent({ prompt: `审查 ${f} 并给出问题清单` }))
)
return { files, results }
概念含义
WorkflowStartRequestscript（脚本正文）、meta（身份块）、args、parent、可选 subagentProvider / maxTotalAgents / signal
WorkflowMetaname / description / whenToUse / phases（仅用于进度展示，不暗示执行结构）
WorkflowResultvalue（脚本返回值）、stopReason（completed / cancelled / error）、agentsStarted
fatal 错误参数写错、未知选项、超上限等 fatal: true 错误会直接终止脚本，绝不会被 parallel() 悄悄吞成 null
⚠️ 失败纪律：拼写错误必须响亮

workflow 的一条设计原则：「一个拼错的选项必须明确报错并终止脚本，绝不能消融为看似普通子 agent 失败的结果。」逐项的 null 只留给「子运行失败」和「阶段内普通脚本错误」；钩子误用一律 fatal。

Agent Teams：持久团队 + 共享任务

实验性的 ctx.agentTeams 在「可继续 subagent」之上，提供更接近真实团队的协作：

👑隐式 Lead
根 agent 自动成为队长
🧑‍🤝‍🧑具名 teammate
可继续的成员，有稳定身份
📬peer inbox
成员之间可直接发消息（不只通过父级）
🗂️共享任务 DAG
任务状态在团队内共享，可依赖编排

此外还有一个面向「不可变目标」的 Ralph 循环：前台启动一个全新 agent 反复尝试同一目标，跨轮次靠「共享工作区 + 有界 Ralph 交接」传递状态，而不是继承对话历史。它是由 workflow 与 subagent 原语组合出来的工具策略，不是另一种循环引擎。

🧪 小测验
spawn 与 fork 一个子 agent 的关键区别是？
答案：B。fork 从父会话的某个已提交前缀「播种」子会话；spawn 是全新子 agent，不接收父历史。
🧪 小测验
在 workflow 脚本里，一个参数拼错的钩子调用会怎样？
答案：B。钩子误用（错误参数、未知选项、超上限等）是 fatal，组合器会直接重抛，不会消融成普通子 agent 失败。
