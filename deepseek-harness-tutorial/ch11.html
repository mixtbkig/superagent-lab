上下文压缩与记忆

模型的上下文窗口是有限的。一个长任务跑了几十轮、读了上千行文件之后，请求就会「装不下」。DSH 不能简单地丢掉旧消息（那会破坏「日志是真源」），于是它用一套精巧的压缩（compaction）机制：把旧历史总结成摘要，用一条 surface 事件「盖住」它。

🎯 学完这一章，你会明白
  • token 计量（tokenMeter）如何为「压力」提供依据；
  • 压缩的三个触发入口：pressure、context-overflow、手动 compactNow；
  • compaction/start|summary|end 事件与「锁」的作用；
  • 工具结果剪枝与图片省略：压缩前的两步「减重」。
🧸 小学生版：把厚笔记做成摘要卡

你的笔记本写满了 200 页，书包快装不下了。你不能撕掉旧页（老师要检查过程），于是你：

  • 先把重复的草稿纸（工具结果）挑出来精简一下；
  • 再把前面的 150 页浓缩成一张「第 1–150 页摘要卡」，夹在笔记本里；
  • 以后复习只看摘要卡 + 最近 50 页；旧页还在，需要时可翻。

这正是 DSH 压缩做的事：先剪枝，再摘要，旧日志不删，只「盖住」。

先量一量：tokenMeter

压缩的前提是「知道现在有多满」。ctx.tokenMeter 是一个可回放的 token 计量服务：它按路由模型（provider + model）估算每次请求的 token 数，并把已消费的日志修订号一起记下，保证同一份日志每次测量结果一致。压缩的「压力」判断、保留尾部策略、以及摘要范围选择，都依赖它。

💡 为什么要「可回放」？

因为压缩决策本身要写进日志（compaction/summary 里带估算 token 数）。如果测量每次不一样，回放就对不上。所以 tokenMeter 必须与日志修订号绑定，做到「同一输入，同一结果」。

三个入口，两种触发

方法触发场景说明
compactIfNeeded(agent, trigger, signal)pressure：agent/pre-step 时按已提交请求头判断「快满了」
context-overflow：agent/request-error 里收到 CONTEXT_WINDOW_EXCEEDED		自动策略的两条路径
compactNow(agent, signal)用户手动 /compact，或空闲会话主动缩减即使没到压力也做一次有效缩减；无有效范围返回 null
compactRegion(...)显式指定一个两端都包含的 surface 范围区域边界保持「工具调用/结果」配对，但不保持整个轮次

压缩怎么写进日志：三事件 + 一把锁

compaction/start获取锁
→
摘要生成ctx.llm.stream()
→
compaction/summary记录摘要与被遮蔽区间
→
追加 user/messagesurfaceOp: replace
→
compaction/end释放锁
锁括住整个操作。中途崩溃会留下「有 start 无 end」的遗留锁，可被检测——而不是一个虚假声称完成的 end。

三个事件都仅写入日志（不是 surface 事件）。compaction/summary 记录：安全摘要、被遮蔽的 surface 边界对（start/end seq，是「位置跨度」不是数值区间）、按 surface 顺序排列的被遮蔽 seq、估算 token 数，以及摘要调用的 provider/model/usage。真正进入模型视野的是那条带 surfaceOp: { op:'replace', startSeq, endSeq } 的 user/message。

💡 为什么 start/end 是「位置」而不是「数值」？

因为一次压缩之后，摘要节点会以一个「新的高 seq」落在「旧区间的位置」上。于是下一轮压缩时，start 完全可能大于 end。真正的权威是被遮蔽节点的完整 seq 列表 shadowedSeqs（按 surface 顺序），而不是那个数值区间。

动手：看上下文怎么「瘦身」

压缩前：全部历史都在请求里
每个小方块代表一段上下文。压缩把旧的一大段折叠成一条摘要（青色），只保留最近一小段原文。

压缩前的两步「减重」

在真正选择「摘要哪一段」之前，compaction-basic 会先做两件更便宜的事：

✂️ 工具结果剪枝

调用可选的 ctx.toolResultPruner，把旧的、冗长的工具结果替换成精简版（单独追加一条新的 tool/result 遮蔽旧的），然后重新测量。很多情况下，光剪枝就够了，根本不用生成摘要。

🖼️ 图片省略

当请求图片超出精确字节预算时，compaction-image-offload 记录一个 image/offload 事件，把最旧的一些图片替换成占位文本，然后重试这一步。

这就是为什么压缩不一定产生摘要：只要剪枝或图片省略推进了 surface 替换代次，恢复重试就有意义；否则仍以原始请求错误为准。

恢复：在「还开着的步骤里」重试

上下文溢出不是「重新开一轮」，而是在失败的步骤关闭后，经 agent/request-error 处理：

  1. 若触发条件满足 → 先剪枝，再选摘要；
  2. 只有剪枝/摘要推进了 surface 替换代次，才返回 { kind:'retry' }；
  3. 重试时不重复组装、不重复 pre-step、不重复用户准入，只复用已冻结的渲染组装重新准备调用。
